# tsc-ts

The TypeScript 7.0.2 compiler (tsgo), ported to TypeScript and compiled to a native executable with [scriptc](https://scriptc.dev). Experimental.

## Installation

```sh
npm install -D tsc-ts
```

npm installs the executable for your platform from an optional dependency:

| Platform                         | Package                    |
| -------------------------------- | -------------------------- |
| macOS, Apple silicon             | `@tsc-ts/darwin-arm64`     |
| macOS, Intel                     | `@tsc-ts/darwin-x64`       |
| Linux arm64, glibc 2.34 or later | `@tsc-ts/linux-arm64-gnu`  |
| Linux arm64, musl                | `@tsc-ts/linux-arm64-musl` |
| Linux x64, glibc 2.34 or later   | `@tsc-ts/linux-x64-gnu`    |
| Linux x64, musl                  | `@tsc-ts/linux-x64-musl`   |
| Windows x64                      | `@tsc-ts/win32-x64-msvc`   |

Don't install with `--omit=optional` or `--no-optional`.

## Usage

`tsc-ts` takes the same arguments as `tsc`:

```sh
npx tsc-ts -p tsconfig.json
npx tsc-ts --noEmit src/index.ts
```

`tsc-ts --api` serves the TypeScript API over stdin and stdout, like `tsc --api`. As there, a project loads the sources of the projects its config references in place of their declaration outputs, unless the config sets `disableSourceOfProjectReferenceRedirect`. On Windows, `--api --pipe \\.\pipe\<name>` serves it over a named pipe it creates, as `tsc --api --pipe` does, for clients that connect to the pipe (such as scriptc under Node.js); only the native executable supports `--pipe`. On macOS and Linux, `--api --listen <path>` serves it on a Unix socket it creates, with mode 0600, to one client of the same user at a time, each until the client closes its end. Each client gets the answers a new `tsc-ts --api` process would give, except that symbol ids continue from earlier clients, and the server reads every file through the client again, but it keeps parsed files between clients and reuses those whose text is unchanged, along with the encoding `getSourceFile` sends for each, so a client that opens the same project again loads it faster. The server exits when no client connects for 60 seconds (`--idle-exit <seconds>` sets the time), or after a client when its resident memory is above 2.5 times what it held after its first client (`TSC_TS_LISTEN_MEMORY` sets the limit in megabytes). To stop, it removes the socket file, serves the clients that had connected, and exits. It replaces a socket file that no server answers on, such as one left by a server that was killed. Only the native executable supports `--listen`. With `--default-libraries-from-disk`, the server reads the files in its default library directory (`TSC_TS_LIB_DIR`, or the executable's directory) from the disk itself, even when the client handles file system calls (`--callbacks`), which saves a round trip to the client for each library file.

With `--api --runExternalCode`, as with `tsc --api --runExternalCode`, the content mappers that the config of a project names run, each as the process its package declares, for as long as a snapshot has a program that uses them. The files they transform are in the program with the text the mappers made of them: `getSourceFile` answers a file with its original text, the map between the two texts, the mapper and what else the mapper returned for it, and a diagnostic in such a file is answered at its place in the original text, or with a last entry in its message chain that says it lies in text the mapper wrote. The files of a transform are kept while a snapshot has them, so a file is transformed again when its text changes or the identity of its mapper in the project does; a change to a file a mapper watches opens the mapper's project again, which may give it another identity. Without the flag, a config that names content mappers gets an error for them, and none runs.

`--checkers N` checks the program on N threads. Unless `--checkers` or `--singleThreaded` is given, the native executable uses one checker per CPU it may run on (up to 16), and at least tsgo's four; it uses fewer than the CPUs, but never fewer than four, when the estimated peak memory of more checkers would not fit 85% of the machine's memory (`TSC_TS_CHECKERS=fixed` keeps tsgo's four), and checkers beyond the fourth stop taking files, one at a time, when the process's memory reaches that share; it shares one program between its threads and also parses and binds the program's files on them. Unless `--singleThreaded` is given, the program's files are parsed and bound on threads also with `--checkers 1` and in the first build of `--watch`, with or without build info, as tsgo does. Files that share costly declarations, such as a large generated schema and the few files importing it, are checked together on one checker. The checker threads share the results they compute where the run expects that to pay: at 12 or more checkers, when 40% of the program's files are declarations or come from `node_modules` and the checkers' ranges mostly resolve the same large libraries. `TSC_TS_SHARE=1` turns sharing on for any program and `TSC_TS_SHARE=0` keeps it off, and a run whose sharing stops paying stops sharing its results as it goes. A sharing run may also bound how many results it posts at a time, which costs a few percent on a project that does not gain by it and saves more on one that does: the learned choice among a project's runs, off until its record shows it faster, and `TSC_TS_SHARE_BOUNDED=1` turns it on for any program while `TSC_TS_SHARE_BOUNDED=0` keeps it off. `TSC_TS_AUTO=0` keeps the choices of a run before automatic selection (fewer checkers where the ranges resolve large libraries, no sharing), and `TSC_TS_AUTO=static` keeps the rules and the in-run switches but reads and writes no records, and `TSC_TS_AUTO=explore` adds the experimental exploration described below. Unless `--singleThreaded` is given, the files are parsed on the CPUs the process may run on, but one, whatever the checker count, and `TSC_TS_PARSE_THREADS` sets how many. `--extendedDiagnostics` prints the checker threads, the sharing and the parse threads after the statistics table, under `Suggestions:`, with where each value came from (`pinned: --checkers`, `default`, `automatic: ...`, `learned: check 14% faster over 3 runs`, `exploring`, `control`) and how to pin it; `--build` prints one section per project it builds. The section also names the run's record under `Records:`. Each run that checks a program writes what it measured to `~/.cache/tsc-ts/runs-v1/` (`TSC_TS_CACHE_DIR` sets the directory, `TSC_TS_CACHE=0` turns records off), for later runs of the same project on the same machine to read. A later run chooses from that record where the rules left a setting open: a configuration the samples show faster than the static choice — by 3% or twice the standard error of the gains each of its samples makes against the nearest run of the other arm, on three samples of each taken while the machine was not busy — is adopted, every sixteenth run (and the first after two weeks) re-measures the static choice as a control run, and an adopted configuration whose last three samples all fall behind the control runs reverts at once. A run never tries a configuration that could make itself slower: it adopts only what the samples already show faster, from `tsc-ts doctor`, from a pinned run or from a run that already used it. `TSC_TS_AUTO=explore` turns on an experimental alternative in which a run also tries a setting the signals leave uncertain: one run in eight tries three quarters of the count where the library text puts it near the cut, sharing at eight checkers near the rule's limits, or half the parse threads, and such a run is slower than the configuration it would have used. A program whose shape changed by more than 15% discards the record's samples. Watch mode, a `--build` of several projects at once, `--singleThreaded`, Node builds and `TSC_TS_AUTO=0` or `static` keep no record, and the section says why; a run with `CI` set reads and adopts but never explores. `tsc-ts doctor [-p <tsconfig>] [--runs N] [--budget SECONDS] [--emit] [--json] [--no-save]` measures these settings on this machine: it runs the project's check under the default configuration, with sharing on, with up to 16 checkers, with both, and with half the parse threads, compares the phase times by the same rule automatic selection uses, and prints what it recommends with the evidence for it. Each measured run is a child process, so it runs as a user's run would, and it writes what it measured to the file named by `TSC_TS_DOCTOR_REPORT`; runs without the variable are unaffected. Doctor stores its samples in the record with role `doctor`, unless `--no-save` is given. The command is experimental: the configurations it compares and what it recommends may change. Under Node.js, where every thread builds its own copy of the program, tsc-ts checks on one thread unless `--checkers` is given. `--incremental`, `--watch` and `--build` always check on one thread. The diagnostics are the same as with one checker, except for the two a check reports when a type instantiation reaches the depth limit: TS5115 on the instantiations, and TS2344 on the constraint check that stops there. Whether a file reaches the limit depends on the declarations its checker has already resolved, and which files a checker has is decided while checking runs, so those two diagnostics are best effort with more than one checker: one run can report them in different files than another run, and a run with one checker can report them where a run with several does not.

The native executable never frees syntax trees, types, signatures or symbols: it keeps them until it exits, which saves the cost of tracking them during a build. A one-shot build is unaffected, but a long-running process grows with each rebuild or project update. Native `--watch` (also with `--build`) runs in a child process, and when a change arrives while that process holds more than 2.5 times the memory it held after its first build, a new process replaces it and builds the change, reporting what the old process would have. `TSC_TS_WATCH_MEMORY` sets that limit in megabytes, and `TSC_TS_WATCH_MEMORY=0` turns the replacement off. A `--api` process grows with each project update; restart it to reclaim the memory.

The default lib files (`lib.*.d.ts`) ship next to the executable. Set `TSC_TS_LIB_DIR` to use another directory.

## Programmatic API

`tsc-ts/api` describes tsc-ts's programs, checkers, nodes, symbols, types and signatures in TypeScript, with the names and numbering of TypeScript 7's API (`typescript/unstable/sync`): the node interfaces, `Symbol`, `Type` and its kinds, `Signature`, `IndexInfo`, `TypePredicate`, `JSDocTagInfo`, `Diagnostic`, `Program`, `TypeChecker`, `CompilerOptions`, and the enums `SyntaxKind`, `NodeFlags`, `ModifierFlags`, `TokenFlags`, `SymbolFlags`, `TypeFlags`, `ObjectFlags`, `ElementFlags`, `SignatureFlags`, `SignatureKind`, `IndexKind`, `TypePredicateKind`, `TypeFormatFlags`, `NodeBuilderFlags`, `ScriptTarget`, `ModuleKind`, `ModuleResolutionKind`, `ModuleDetectionKind`, `ScriptKind`, `LanguageVariant`, `JsxEmit`, `NewLineKind`, `DiagnosticCategory` and `InternalSymbolName`.

```ts
import { isIdentifier, type Node } from 'tsc-ts/api';

const nameOf = (node: Node): string | undefined => (isIdentifier(node) ? node.text : undefined);
```

The type guards are those TypeScript 7's API generates, with the same names and kinds. Each node interface that has kinds of its own has one named after it: `isIdentifier(node)`, `isCallExpression(node)`, `isVariableDeclaration(node)` and so on. So does each union of node interfaces whose kinds are listed, such as `isClassLikeDeclaration`, `isFunctionLikeDeclaration`, `isSignatureDeclaration`, `isAccessExpression` and `isModifier`, and each token type, such as `isTrueLiteral`, `isThisExpression` and `isBinaryOperatorToken`. The guards of sets of kinds take a kind: `isAssignmentOperator(kind)`, `isModifierKind(kind)`, `isTokenKind(kind)`. A guard answers by the node's kind; one that accepts import or type alias declarations also accepts the declarations a JSDoc `@import` or `@typedef` makes in a JavaScript file (`SyntaxKind.JSImportDeclaration`, `SyntaxKind.JSTypeAliasDeclaration`), as TypeScript 7's do. `isExpression(node)` and `isTypeNode(node)` are TypeScript 7's hand-written guards of those names, and `hasInitializer(node)` answers whether a node is of a kind that has an `initializer` (`HasInitializer`), whether or not it has one. The base interfaces of statements, expressions, type nodes and class, type and object literal elements, which have the same members, declare TypeScript 7's brand members (`_statementBrand`, `_expressionBrand`) as optional members that no node has, and `ObjectType`, `UnionType` and `IntersectionType` declare one each, so that where a guard answers false, the value keeps a type: after `if (isExpression(node)) return;`, a `Node` is still a `Node`, and a `Statement | Expression` is a `Statement`.

Lists of child nodes are `NodeList` objects: `node.arguments.nodes` holds the nodes, and `pos` and `end` the list's range. A node's `parent` is typed `Node`, as in TypeScript 7's API, so `node.parent.kind` needs no check; the `parent` of a source file is undefined. `symbolName(symbol)` gives a symbol's name as TypeScript 7's API does (`__call`, `export=`).

### Programs and checkers

`createProgram({ rootNames, options, host })` creates a program of root files with compiler options, and `createProgramFromConfigFile(configFileName, host)` the program of a `tsconfig.json`. `parseConfigFile(configFileName, host)` returns a config file's options, root files and diagnostics. A program loads its files as `tsc-ts` loads a project's, on the calling thread, except for the projects a config file references: as the projects of `tsc --api` do, the program loads the sources of a referenced project in place of its declaration outputs, whether they are built or not, and reports no errors in those sources. With `disableSourceOfProjectReferenceRedirect` in the config, it loads the declaration outputs, as `tsc-ts -p` does.

```ts
import { createProgramFromConfigFile, SyntaxKind, walkPreorder } from 'tsc-ts/api';

const program = createProgramFromConfigFile('tsconfig.json', {
  getCurrentDirectory: () => process.cwd(),
  useCaseSensitiveFileNames: () => process.platform === 'linux',
  getDefaultLibraryDirectory: () => '/path/to/lib',
});
const checker = program.getTypeChecker();
for (const file of program.getSourceFiles()) {
  if (program.isSourceFileDefaultLibrary(file)) continue;
  walkPreorder(file, (node) => {
    if (node.kind === SyntaxKind.Identifier) console.log(checker.typeToString(checker.getTypeAtLocation(node)));
  });
}
program.dispose();
```

The host's `getDefaultLibraryDirectory()` names the directory with TypeScript 7's `lib.*.d.ts` files; the platform packages carry them in their `lib` directory. The host's `readFile`, `fileExists`, `directoryExists`, `realpath` and `getAccessibleEntries` are optional: where one is missing or answers undefined, the program reads the disk.

The program's diagnostics, with their text and positions, are those `tsc --api` returns for the same project. `getTypeChecker()` returns a checker for queries, separate from the checker that reports the program's diagnostics, so queries don't change them. Its methods answer as the `tsc --api` requests of the same names; `getJsDocTagsOfSymbol(symbol)` answers as the `getJsDocTags` request: the JSDoc tags of a symbol's declarations, each with its `name` and, where it has one, its `text`, which is what the tag names or types followed by its comment. The ones TypeScript 7 always answers return a type or a signature, never undefined: `getTypeAtLocation`, `getTypeOfSymbol` and `getTypeFromTypeNode` give the error type (`type.isErrorType()`) where there is no type, and `getResolvedSignature` the unknown signature for a call that doesn't resolve. Nodes, symbols, types and signatures are tsc-ts's own objects, one per node, symbol, type and signature in a program, so they can be compared with `===` and used as Map keys.

The checker also answers about symbols as TypeScript 7's `Checker` does: `getExportsOfModule(symbol)` returns the symbols a module exports, those of its `export *` declarations included, in the checker's order of symbols; `getParentOfSymbol(symbol)` the symbol a symbol is a member or an export of, with its declarations merged (the `getParentOfSymbolForChecker` request of `tsc --api`; `symbol.getParent()` gives the parent as bound); `getExportSpecifierLocalTargetSymbol(node)` the symbol an export specifier exports; and `isUnknownSymbol(symbol)` whether a symbol is the one `getAliasedSymbol` returns for an alias that doesn't resolve.

About a type, the checker answers `getApparentType(type)`, the type whose members a value of it has; `getBaseConstraintOfType(type)`, the constraint of a type parameter or of another generic type with the constraints in it resolved, and for a union or an intersection the one of its members' constraints; `getWidenedType(type)`, the type as a declaration infers it from an initializer, where the object literal types of a union get each other's missing properties and, without `strictNullChecks`, `null` and `undefined` become `any`; `getAwaitedType(type)`, the type `await` gives; and `getIndexTypeOfType(type, kind)`, the value type of its index signature with a string (`IndexKind.String`) or a number key, which is the value type of the `getIndexInfoOfType` request of `tsc --api`. `getBaseConstraintOfType`, `getAwaitedType` and `getIndexTypeOfType` return undefined where there is no such type.

About a signature, it answers `getParameterType(signature, index)`, the type of the parameter at an index, which at and after a rest parameter is its element type, and `any` after the last parameter without one (a negative index throws a `RangeError`); and `isUnknownSignature(signature)`, whether a signature is the one `getResolvedSignature` returns for a call that doesn't resolve.

`parseSourceFile(fileName, text, options)` parses one file without a program, as a program with `options.compilerOptions` parses it. The node functions `forEachChild`, `walkPreorder`, `tokenStartOfNode`, `getJSDoc`, `getModifiers`, `canHaveModifiers`, `getCombinedModifierFlags`, `getCombinedNodeFlags`, `getLineStarts`, `getLineAndCharacterOfPosition`, `getPositionOfLineAndCharacter` and `tokenToString`, and `flattenDiagnosticMessageText`, behave as TypeScript 7's. `getSourceFileOfNode(node)` returns the source file a node is in, and `getTextOfNode(node)` its text from the start of its first token, as TypeScript's `node.getSourceFile()` and `node.getText()` do. `getChildren(node)` returns a node's children with the tokens the parser doesn't keep, such as `(`, `,` and `;`: its JSDoc comments, then its child nodes and the tokens between them in source order, with each list of children as one `SyntaxList` node. `getFirstToken(node)` and `getLastToken(node)` return the first and last token among them. They answer as TypeScript 7's `node.getChildren()`, `node.getFirstToken()` and `node.getLastToken()`, and make the tokens of a node once, so two calls return the same nodes. `getJSDocTags(node)` returns the JSDoc tags that apply to a node, as TypeScript 7's function of that name does: the tags of the last JSDoc comment of the node, of its initializer and of each declaration or statement it is a child of and that documents it (the first declaration of a variable statement is documented by the statement), with the `@overload` tags of earlier comments, and for a parameter or type parameter the `@param` or `@template` tags of its declaration that name it.

`createScanner(skipTrivia, languageVariant, text)` returns a `Scanner` of a text, with these methods of TypeScript 7's scanner: `scan`, `getToken`, `getTokenFullStart`, `getTokenStart`, `getTokenEnd`, `getTokenText`, `getTokenValue`, `getTokenFlags`, `hasPrecedingLineBreak`, `isUnterminated`, `reScanGreaterToken`, `reScanSlashToken`, `reScanTemplateToken`, `scanJsxToken`, `reScanJsxToken`, `getText`, `setText`, `setLanguageVariant` and `resetTokenState`. `getLeadingCommentRanges(text, pos)` and `getTrailingCommentRanges(text, pos)` return the comments before the next token at a position and after a position on its line, and `skipTrivia(text, pos)` the position where the next token starts, as TypeScript's functions of those names do. The scanner is the compiler's, so where TypeScript 7's compiler scans differently from the scanner of its JavaScript API, it scans as the compiler: a shebang is trivia before the first token whether or not trivia is skipped, a `#!` elsewhere is one `Unknown` token, a single-quoted string has `TokenFlags.SingleQuote`, and `getToken()` answers `JsxText` after `scanJsxToken()` reads text.

`createProgram({ rootNames, options, host, oldProgram })` and `createProgramFromConfigFile(configFileName, host, oldProgram)` take the parsed files of `oldProgram`, a program of `tsc-ts/api`, instead of parsing them again, where a file has the same name, text and module detection options, as TypeScript 5's `oldProgram` does with a host that keeps unchanged files. The new program resolves its modules and checks anew, so it answers what a program created without `oldProgram` answers, and it does not depend on the old program, which stays usable and is disposed of separately.

`program.updateFile(fileName, text)` returns the program with one file's text replaced, as TypeScript 7 updates a program whose only change is one file: the new program takes every other file, the options and the module resolutions from the program it was called on, which stays as it was, so it is created in the time it takes to parse the file. It answers what a program created from the new text answers. It returns undefined when that needs a new program: the file is not in the program, is a `package.json`, belongs to a package installed more than once, or no longer imports, references or needs the same modules. The two programs are disposed of separately.

`getPreEmitDiagnostics(program, sourceFile?)` returns a program's config file parsing, program, syntactic, global and semantic diagnostics, sorted and without duplicates, as TypeScript's function of that name does.

An exception the compiler throws while answering a call reaches the caller as an `InternalCompilerError`, with the exception as its `cause`; the program's checker may be inconsistent after one, so dispose of the program. `program.dispose()` frees the program's checkers; calls on the program or its checker after it throw a `DisposedProgramError`.

The package has a JavaScript build with declaration files for Node.js, and the TypeScript sources of the API and the compiler (the `source` export condition) for compilers that build it from source. The sources compile with scriptc: a test builds a program on `tsc-ts/api` natively and checks that it answers as the Node build.

The API imports `@scriptc/threads`, an optional peer dependency that the command line doesn't use. Install it next to `tsc-ts` to use `tsc-ts/api`:

```bash
npm install -D tsc-ts @scriptc/threads
```
